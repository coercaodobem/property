# Property State-Machine Inventory and Architecture Decision

**English** · [Português (Brasil)](state-machines.pt-BR.md)

Audit snapshot: `modelo-mvp` at `7e92abb6cebb5fee7b4344963ba4a30ad831487c`, 2026-11-08. This inventory covers Property-owned browser code in `property/web/` and the Property campaign/payment adapters in `property/relay/`. It does not claim to enumerate browser internals, bundled vendor code, or the reused Geode implementation.

## Decision

Adopt **small, explicit state machines owned by each workflow**, with the machine snapshot as the single source of truth for that workflow. Do not replace the app with one global state machine, add a framework, or rewrite every flow at once.

Use a machine when a workflow has multiple asynchronous stages, retries, terminal outcomes, persistence, or resource cleanup. Keep independent preferences, simple selections, and presentation-only toggles as ordinary local state. A machine owns its transitions; the UI renders a localized view of its snapshot. Side effects such as relay I/O, IndexedDB, media capture, and payment RPC stay behind the machine's commands.

This gives people coherent progress, recovery, and error messages; gives maintainers one place to inspect legal transitions and invariants; and gives coding agents stable machine IDs, source ownership, events, and safe snapshots. Incremental migration protects existing protocol formats, database records, and working behavior.

### Contract for future migrations

Each stateful workflow should document or expose:

- stable `machineId`, current `state`, monotonic `revision`, and non-secret context;
- accepted events, guards, legal transitions, and terminal states;
- entry/exit effects and cleanup ownership;
- user-visible progress, recovery action, and localized error mapping;
- persistence/restart behavior and idempotency rules;
- deterministic transition tests, including stale async results and failure paths.

Snapshots must never contain private keys, passwords, message bodies, recovery material, or raw payment credentials. Unknown events and illegal transitions must be rejected without partially mutating the workflow. Keep wire events, Nostr kinds, IndexedDB schemas, and existing user choices unchanged unless a separately reviewed change requires otherwise.

Some modules already publish status snapshots; other workflows are inferred from nullable fields, booleans, timers, collections, browser APIs, or DOM classes. Pure parsers and value modules such as money conversion, payment URI parsing, message-day labels, location-card rendering, and Nostr entity validation are not machines by themselves. They become part of a machine only when their result is persisted or drives a multi-step user workflow.

## Migration order

1. **Keep this inventory as the discovery map.** New stateful flows add a stable ID and owner here before they spread across the app.
2. **Formalize `app.boot-auth` and `storage.local` first.** They control key lifetime and whether the workspace is safe to use. Model database readiness, locked/unlocking/activating/ready/locking, cancellation, and recoverable errors without changing vault format or auto-lock policy.
3. **Formalize `relay.connection` and `relay.bridge`.** Keep per-relay connection truth separate from publish acknowledgement, bridge configuration, and background availability. Render status from snapshots.
4. **Preserve `media.call` and `media.direct-transfer` behavior while adding explicit transition tables and deterministic tests.** These already own state but have the highest cleanup/race complexity.
5. **Migrate remaining workflows only when touched.** Avoid a risky one-shot rewrite. Each change must preserve persisted records and protocol semantics and document its transition evidence.

The largest direct improvement is to stop using DOM classes/disabled controls as an independent source of domain truth. Machines own workflow state; the view reflects it. Accessibility, user-facing text, and English/Portuguese localization remain part of each transition, not an afterthought.

## Evidence and limits

This is a source inventory, not proof that every browser/platform path has been exercised. It was derived from the current Property controller, the modules loaded by `web/index.html`, the stateful relay adapters, and the product boundaries in `README.md`/`AGENTS.md`. It makes no claim that the currently present campaign engine is enabled, that browser background execution is continuous, or that a source-level transition has passed an end-to-end test. No runtime state or protocol was changed in this decision.
