# Ghostly UX adapted inside Property

[Ghostly](https://github.com/MiguelMedeiros/ghostly) is an upstream reference for conversation interactions and interface details. Property has one user-facing app: its existing PWA at `https://coercaodobem.github.io/property/`. This integration adapts selected interaction patterns inside `property/web/`; it does not add a second app, identity, message store, or transport.

## Product boundary

- Keep Property's existing Nostr identity, local message store, Nostr events, and device-saved relays. Fresh installs receive a locally stored random pair from the bundled list and can replace it.
- Adapt compatible interactions inside the Property PWA and use its existing relay connections.
- Do not bundle or publish a second Ghostly-derived client. Ghostly is a design reference, not a runtime dependency.
- Adapt protocol-dependent behavior to Nostr. Features that cannot be carried safely by the current Nostr flows stay out until they have a compatible design and validation gate.

## Integrated in Property

- The Ghostly-inspired project story is presented at `property/web/about.html` and `about.pt-BR.html` as part of the existing Pages/PWA bundle. It uses Property’s brand, explains the product with a responsive step-by-step narrative, and is cached for offline reading; it is not another app. The first-use relay section states that Property picks and saves two bundled secure relays when none are configured, while explaining that a relay can be unavailable and can see IP/public metadata.
- Private-message replies use the NIP-17 `kind:14` `e` reference to the parent message. Property creates one rumor and wraps that same event for both participants, so its reply ID is consistent on both devices. Received replies keep the rumor event ID. The reply preview and jump action use local history only.
- On touch and pen, a rightward swipe on a message with a Nostr event reference starts the same reply flow; vertical scrolling, links, controls, code, and messages without an event reference are ignored. In an empty composer, `ArrowUp` opens the latest eligible sent message in the existing editor. A draft, IME composition, modifier key, open dialog/picker, or active edit keeps its normal behavior; cancel restores the draft. Both shortcuts only change local UI state until the person explicitly sends or saves.
- Private reactions use NIP-17 gift wraps containing NIP-25 `kind:7` reactions. They remain in the same chat and use the participants' configured inbox relays.
- Direct and group chats show a temporary typing indicator inside the current conversation. Property sends a `kind:21059` ephemeral NIP-59 gift wrap containing a minimal encrypted `kind:20000` rumor (`typing` or `stop` plus a sequence); message text is never included or stored. The receiver only displays activity for an already-known active conversation, drops stale or reordered signals, and clears the label on `stop`, a received message, or local expiry. People can disable outgoing typing indicators per identity. Independent Property agents can use the same event type to show a fixed `thinking` state in a direct chat; it contains no custom text, expires locally after at most 60 seconds, and stops on a sent message or daemon lock when possible. The relay sees the recipient routing tag, sender connection metadata, and timing, but not the encrypted activity payload; kind 21059 relays must not store the event.
- Optional active status is shared only with the other person in an open direct chat. The setting in Profile and security is off by default. While enabled, the foreground PWA sends an encrypted ephemeral `kind:21059` signal on entry and every 30 seconds; it sends an inactive signal when the person leaves or backgrounds the chat when possible, and receivers expire active status after 75 seconds. It never targets groups or publishes a public online event. Relays can see recipient routing and connection metadata, but not the encrypted status. This is best-effort foreground presence, not a background guarantee.
- Optional per-identity read receipts are off by default. After someone enables them, Property sends a Property-specific encrypted ephemeral `kind:21059` signal only to the author of a received message when its row is visibly on-screen. A group receipt goes only to that message's author, not to the full room. It contains the Nostr message event ID, never message text, and travels through the existing inbox-relay route; relays can still see the recipient routing tag and connection metadata. The author must be online and may miss the signal. A receipt means the message was visible in this PWA, not that a person understood it or that relay delivery succeeded. The preference stays local, incoming receipt records are stored only on this device and capped at 500 recent messages, and agent-protocol messages do not send receipts. This Property action is not a standard NIP-17 feature.
- People can edit their own delivered private and group messages from the existing message menu. Property sends a replacement NIP-17 `kind:14` rumor and an encrypted `kind:5` tombstone for the old rumor, with a bounded sequence and stable root ID inside the encrypted events. Property clients merge the replacement in place, keep the original timestamp and reply/reaction references, accept edits that arrive before the original, and resolve same-sequence concurrent edits by event ID so relay order does not decide the visible result. The editor runs the local secret warning before publishing and does not edit structured agent-protocol messages. The edit tag is a Property extension: clients that do not implement it may display the replacement separately; real relay delivery can be partial and is reported as such.
- Private group conversations are created from the existing New conversation flow and stored in Property's existing conversation and message stores. A room is keyed by its sorted participant public keys. Messages use a NIP-17 `kind:14` rumor with the other members in `p` tags and an optional `subject`; Property creates a separate gift wrap for every participant, including the sender, and routes each envelope to that participant's published kind-10050 inbox relays. The client caps rooms at 10 participants, including the sender, and supports replies, reactions, saved messages, and forwarding in the same conversation UI.
- NIP-17 rooms do not provide membership approval, an administrator, or reliable leave/removal controls. Each member must already have published an inbox list that the sender can discover through their configured relays. Create a room with people who have agreed to participate. Groups larger than 10 need a more suitable protocol.
- Messages can be bookmarked in the existing local message store. Bookmarks stay on this device and are not published to relays.
- Message Details opens from a message's action menu and shows the NIP-17 inner rumor reference, sender key, timestamp, reply reference, and this device's relay-acknowledgement state. Its optional JSON copy contains only that metadata, never message text or private keys. The panel explains that relay acknowledgements are not proof the recipient read the message and that relays store encrypted gift wraps rather than the inner rumor.
- The profile and security panel adapts Ghostly's identity surface to the existing Property key and Nostr kind 0. A person can load the latest signed profile from saved relays, edit the public name, About, HTTPS website, HTTPS picture URL, and NIP-05 field, then publish through those relays. Updates preserve metadata fields this editor does not own. Changes are also stored locally; when relays cannot be reached, Property does not publish a partial kind-0 event. The picture URL remains metadata and is never fetched by Property. A separate, explicit NIP-05 action checks whether the domain currently maps the identifier to this Nostr public key. It does not run on profile load and does not verify a real-world person.
- The conversation details panel adapts Ghostly's public contact profile to Nostr kind 0. A person chooses when to query the saved relays and the relay hints for that contact; Property verifies the event signature, stores only bounded profile fields per contact, and may use the signed display name when no local nickname is set. Names and descriptions remain self-described. The optional NIP-05 check is also user-triggered and reports only whether the domain mapping matches the contact's public key; it makes a direct HTTPS request to that domain, exposing the requester's IP address, and may be unavailable when browser CORS rules block the response. Property does not claim real-world identity verification, fetch profile pictures, or contact identity domains without an explicit tap. A website link is opened only when tapped.
- Forwarding creates a new encrypted NIP-17 message from the same Property identity for each selected existing conversation, keeps the body unchanged, and adds a bounded `forwarded` hop marker inside the encrypted rumor. The sender and recipient see a localized badge; the marker is self-reported and does not expose or authenticate the original author. Relays see neither the body nor the inner marker. The result reports local copies separately from relay-confirmed envelopes; it does not claim delivery solely because a copy was saved locally.
- In-chat search filters the current conversation's locally rendered messages. It ignores letter case and accents, highlights matches, and lets the person move between results. It does not search relays, publish a query, or place it in the URL.
- Conversation-list search also scans message history already saved in this browser across direct and group chats. It ignores letter case and accents, shows the newest matching message per conversation, and opens that message when selected. The search stays on this device and is never sent to a relay.
- A conversation can be pinned or unpinned from its existing list menu. Pinned conversations sort first within their current folder, then by recent activity; the pin is stored on this device and never sent to a relay.
- Private-message bodies now use Ghostly's safe, local text-rendering pattern for bold, italic, strike-through, inline/fenced code, spoilers, headings, quotes, lists, and visible HTTP(S) links. The original message bytes stay unchanged in the NIP-17 rumor. Rendering uses text nodes and DOM elements, never HTML parsing; links display their own address, reject hidden-control and credential-bearing URLs, open in a new tab without a referrer, and spoilers stay covered in chat-list previews.
- Link previews are an opt-in action in the existing composer. Property first shows the exact HTTPS URL and discloses that the site may see the sender's IP; only a second explicit tap requests bounded title/description metadata directly from the sender's device. The request omits cookies and referrer, rejects redirects and non-HTML responses, and never loads remote images. CORS may make a site unavailable. The text-only preview tag travels inside the encrypted NIP-17 rumor; the recipient never fetches the URL when opening the message. Preview text is sender-provided, not authenticated page content, so the app labels it and asks people to verify the link before opening it.
- Valid NIP-19 `npub` and `nprofile` references in message text render as Property-styled contact cards. Tapping one opens the existing New conversation dialog with the public code ready for review; it does not query relays, create a conversation, or publish an event. Invalid codes, references inside code spans or URLs, and references after the three-card per-message limit remain ordinary message text. Search and previews preserve the original code. The parser and renderer run from the locally bundled PWA and do not fetch a profile until the person continues through the normal conversation flow.
- The composer exposes one-tap controls for bold, italic, strike-through, inline code, and spoilers. Selecting text wraps the local draft; with no selection, the caret stays inside the inserted markers. These controls never rewrite a sent event or add protocol metadata.
- The composer also includes Ghostly's emoji picker pattern: searchable categories, recent emoji and skin tones. Its Unicode 15 catalog is bundled under the MIT license and cached with the PWA, so opening it makes no external request and works offline. Search understands English names plus common Portuguese terms. Selection inserts the emoji at the draft caret, saves recent emoji per local identity, and publishes nothing until the person presses Send. Message reactions keep the quick choices and can also select any emoji supported by the same bundled catalog; the draft stays untouched, and the chosen emoji is sent only as a NIP-25 reaction inside the existing NIP-17 private envelope flow.
- Conversation folders adapt Ghostly's chat-list organization to this PWA. People can create, rename, reorder, collapse, delete, and assign direct or group conversations; deleting a folder returns its conversations to Other chats. Search stays a flat list across folders. Folder names, order, collapse state, and assignments are saved per identity on this device and never published or synced. New incoming messages increment a local unread count in the conversation and folder list; opening the conversation clears it on this device. Unread counts remain local and do not sync to other devices; read receipts are a separate optional feature described above.
- Unsent drafts are saved locally per Property identity and conversation, so switching chats or locking and reopening the same identity does not mix or lose them. Drafts stay in the local database, are not published to relays, and clear when the message is sent or the draft is erased. Items in the share inbox remain separate until the person reviews and sends them.
- Optional browser notifications are enabled only after an explicit tap and browser permission. Notices are generic and omit message text and contact names. People can mute notifications per conversation for fixed intervals; these settings stay local per identity and do not affect unread counts or relay events. They work only while the app is open and able to receive relayed messages; no push service or background wake is used.
- An optional, off-by-default app icon badge adapts Ghostly's Badging API inside the same Property PWA. After a person enables it in Profile and security, the installed app icon reflects the aggregate unread count stored locally for the active identity. The count and preference are never published; no Notification permission is requested. Browsers without the API keep the in-app unread counts and report the badge as unavailable.
- Before sending a private message, forwarding a message, publishing a Hangout post, or publishing a marketplace offer, the app checks locally for recognizable recovery phrases, private keys, Bitcoin node credentials, and ecash tokens. A match opens a cancel-first warning naming the destination but never displaying or saving the matched text; cancel keeps the draft, while an explicit Send anyway continues. The detector uses the bundled English and Portuguese (Brazil) lists and makes no network requests. It is a pattern check, not a guarantee that every secret format is recognized.
- A contact can be shared from the existing profile as a Property URL, NIP-19 `nprofile`, or QR. The URL carries only that public profile code in its fragment, which the PWA removes before normal app boot; after identity activation it pre-fills New conversation and waits for the person to open it. The QR is generated from local bundled code. Up to three selected secure relay hints may be included and are disclosed in the dialog; no private key, inbox list, message, auto-created conversation, or outbound event is included.
- Re-rendering an open conversation keeps the visible message anchored when the person is reading older messages. If they were already at the bottom, the conversation stays at the bottom.
- When the person has scrolled away from the latest messages, a small Property-yellow jump button counts new incoming messages while keeping the visible message anchored. It clears when the person returns to the bottom; a message they send returns the view to the bottom and is never counted as incoming. Older history catch-up and repeat renders do not increase the count. The count and scroll position remain local.
- These interactions use the existing black-and-yellow Property brand and English/Português (Brasil) language choice.
- On a fresh install, the same PWA randomly selects two relay URLs from a small list bundled with the app and saves them locally. The exact pair is shown on the first screen before identity creation, with a direct option to change relays; no address entry or relay setup is required. It connects after identity activation. If no NIP-17 inbox list is available, the settings dialog pre-fills those selected URLs as a suggestion, so people do not need to discover or type relay addresses. Publishing kind 10050 remains an explicit action because it makes the routing URLs public metadata; the dialog explains that message contents remain encrypted. Both participants still need a published inbox list for NIP-17 delivery. Public relays can see the user's IP address and public event metadata, so the onboarding copy discloses this.
- On mobile, the existing conversation list opens as a drawer inside the same PWA. The current Property conversation store and relay connections remain the only source of chat state.
- The profile can publish a signed NIP-39 kind 10011 GitHub claim through the saved relays. The person can copy the canonical npub proof text, create a public Gist themselves, and publish the GitHub username and Gist ID; publishing is an explicit action. A contact loads the signed claim from Nostr first, with no GitHub request, then chooses whether to verify it. Verification makes one bounded, credential-free request to the fixed GitHub Gist API and can expose the contact's IP address. Other NIP-39 providers remain visible as unverified claims; Property does not equate a signed claim with proof of real-world identity.
- The empty conversation screen adapts Ghostly's “New chat” and “Join” actions to Nostr identities: open New conversation with an npub/nprofile/Property link, enter using a contact code, or share the user's own contact link/QR. These actions reuse the existing dialog, identity, QR generator and relay hints; opening a conversation or sharing a contact publishes no message and reveals no private key. The screen explains encryption and that Property selects relays automatically when none are saved.
- If no relays have been saved yet, Property randomly selects two from its bundled relay list, saves them on the device, and shows the selection with an option to change it. Relay setup is not a first-use requirement.
- A local Web Locks gate lets only one tab per browser storage area open the Property identity, IndexedDB, and relay sockets. Other tabs show a Property-branded waiting screen and start automatically after the active tab closes. Browsers without Web Locks still work but show a notice to use one tab at a time. The gate releases on page exit and reloads a page restored from the back-forward cache.
- The Property PWA accepts text and links shared from another app through its Web Share Target. A service worker enforces a 64 KiB request limit and stores at most 10 pending items in local IndexedDB; shared text is never copied into the redirect URL. The recipient chooses a conversation, reviews the draft in the normal composer, and taps Send to publish through Property's existing NIP-17 path. Later keeps the item locally, Discard removes it, and files are not accepted. A full queue rejects the new share without deleting existing items.
- When a shared item opens a second Property tab while another tab is active, the tabs use a local `BroadcastChannel` signal to open or refresh the existing share inbox in the active tab. Only the launch result is signaled; the shared content remains in the existing local IndexedDB queue. The recipient still reviews the item and explicitly chooses whether to send it.
- The sign-in and profile screens expose an Install Property action. Browsers with a native install prompt ask only after the person taps it; other browsers show local instructions, including Safari's Add to Home Screen steps. The installed app exposes shortcuts for New conversation, Hangout, and Marketplace, which reopen the same Property PWA and wait for identity activation before opening a screen.
- Private conversations group local messages under sticky date headings, using Today/Yesterday or a localized weekday and date. The headings derive from each saved message timestamp, update after local midnight, and do not add protocol events or alter message contents.
- GitHub Pages builds and publishes only the Property PWA from `property/web`.

Reply tags and Chat Rooms follow the current [NIP-17 definition](https://github.com/nostr-protocol/nips/blob/master/17.md), including its guidance to use a more suitable protocol for rooms larger than 10 people. Message bodies and local quote previews remain encrypted or local; relays do not receive their plaintext.

- A `geo:` URI or coordinate-bearing Google Maps, Apple Maps, or OpenStreetMap link in a message produces a local location card with the place name and coordinates. The card is parsed on-device; Property does not load map tiles, geocode the place, or contact a map site while rendering. The person must tap Open in map, which opens OpenStreetMap and shares the coordinates and device IP with that service. The original message remains in the encrypted NIP-17 rumor.
- Voice notes are recorded with the browser's microphone API, reviewed locally, and sent only after an explicit tap. Received recordings can be played at 1×, 1.5×, or 2× and downloaded in their original format. Property puts the audio bytes in a Property-specific tag inside the encrypted NIP-17 rumor, enforces a 400 ms–10 s duration, an 18,000-byte audio limit, and a 60,000-byte wrapped-event limit, and verifies SHA-256 before playback. No audio upload service, remote media URL, transcription, autoplay, or background recording is used. NIP-17 clients that do not recognize the tag still see the encrypted fallback text “🎤 Voice message” but cannot play the audio. Recording is discarded when the page leaves the foreground; voice notes are unsupported in agent-protocol conversations.
- Private and group conversations support reviewed file attachments in the existing composer. Raster images show inline after hash verification; supported audio and video formats have local, user-controlled players with no autoplay. Each file is limited to 2 MiB, a send can contain at most five files and 4 MiB total, and each attachment is split into 12,000-byte chunks. Each chunk is a separate NIP-17 encrypted message, with SHA-256 checks for chunks and the assembled file; conflicting or incomplete transfers never enable download. A partial send keeps the draft and its transfer ID so the sender can retry; repeated chunks coalesce safely. The name, MIME type, caption, and bytes stay inside the encrypted rumor. There is no file upload service. Other NIP-17 clients may show the fallback text but do not know how to assemble the Property attachment tag. Attachments are not enabled in agent-protocol conversations.
- Direct audio and video calls are available between known, unblocked human one-to-one conversations in the same Property PWA. Users review an IP disclosure before starting, then the browser asks for microphone access and, for video, camera access. Offer and answer SDP are validated and sent only to the other participant in temporary NIP-59 encrypted `kind:21059` gift wraps via the recipient inbox relays; audio and video use a direct WebRTC connection. The peer may learn the other device's network IP, and the configured public Google STUN servers also see the connecting IP. Property provides no TURN relay, so some networks cannot establish a direct media path. Calls ring only while Property is open and connected to inbox relays; mobile operating systems may suspend the PWA. Property does not record call media. Deterministic offline controller tests use fake media tracks and peer connections; real-browser, device, and cross-network call validation remains pending.

## Not claimed as integrated

Ghostly-style direct peer-to-peer file transfer, always-on presence, background push notifications, identity proofs beyond NIP-05 mapping and the explicit NIP-39 GitHub Gist check, wallet cards/payments, and signed mini-apps are not claimed as integrated. Property attachments use the existing NIP-17 relay path, not Ghostly's independent P2P transport. The existing share target still queues only text and links locally; chat attachments use the separate composer flow. Each remaining feature needs a Nostr-compatible design, security review, and fixed-count validation. The share target is limited to browsers/operating systems that expose PWA Web Share Target; platform-specific availability remains pending until tested. A mobile PWA may be suspended by the operating system and is not an always-on relay.
